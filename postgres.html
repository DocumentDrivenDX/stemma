1 The question, and a thesis revised twice

The report, The Cost of One Writer, opens with its question:

This report asks when PostgreSQL is a sound default for a web application’s primary datastore.

A thesis is the answer a report argues for. The research log, kept beside the report, records two that were dropped. These are its words.

  1. Throughput ceiling

    PostgreSQL is a sound default until an application's write throughput exceeds what one server can do.

    Rejected after reading. Notion's account says vacuum stalled and that upkeep tends to degrade before hardware limits are reached; Sentry's outage was exhaustion of transaction IDs; Figma names vacuum trouble beside an input and output limit. A thesis about throughput alone would have missed what two of the three accounts describe first or most prominently.

  2. Upkeep fails first

    the first limit a growing application meets is vacuum upkeep.

    Rejected as overstated. Figma's account says its earlier scaling work was aimed at processor use, so upkeep was not the first pressure it met, and no source measures which limit ordinary applications meet first.

  3. The thesis kept

    PostgreSQL 18 is a sound default primary datastore for a web application while the application’s writes fit comfortably on one primary server and that server’s upkeep is attended to. The limits to plan for follow from that single write primary: a process for each connection, row versions and transaction IDs that vacuum has to keep reclaiming, and replication that does not divide writes.

    Confidence recorded: medium. The version 18 documentation states each mechanism, and three operators’ accounts report trouble with upkeep or write capacity on large or heavily written databases. Medium, not high: nothing here measures how often ordinary applications meet these limits, the accounts are self-selected, and no other database is compared.

The confidence and the reason are the model’s own judgement, recorded so that you can weigh them. No check judges them.

The claim it bears on

A claim is something the report asserts, recorded with how sure its author is and why. A note says what a passage shows, and a link says how the note bears on a claim. A note on this passage says:

Updated and deleted row versions stay until vacuum reclaims them; the ordinary form mostly does not give space back to the operating system. The automatic daemon is described as enough for many installations.

It is recorded as supporting this claim, and the thesis:

Updates and deletes leave old row versions for vacuum, and updates avoid new index entries only under stated conditions.

Confidence recorded: high. Stated in the documentation for vacuuming and heap-only tuples; Pavlo’s account agrees on the mechanism.

The link from this claim to the report runs through the passage. The report’s manuscript does not mark which sentence states which claim, and no check judges whether the note supports the claim.

The sentence and its footnote

In the report, the sentence reads, with the quotation underlined:

Vacuum normally runs by itself, and the documentation calls this enough for much ordinary use: “For many installations, it is sufficient to let vacuuming be performed by the autovacuum daemon”.12

Footnote 12

4 Evidence against

Evidence against a thesis is recorded in the same way as evidence for it, as a note whose link says contradicts. A drawing of part of what is linked to this thesis:

  • Thesis (confidence: medium)

    PostgreSQL 18 is a sound default primary datastore for a web application while the application’s writes fit comfortably on one primary server and that server’s upkeep is attended to. The limits to plan for follow from that single write primary: a process for each connection, row versions and transaction IDs that vacuum has to keep reclaiming, and replication that does not divide writes.

  • Docs: architecture → Supports: a process each → Thesis

    Each client connection is served by its own server process, forked for it. This note supports the thesis. It rests on one passage of “Architectural Fundamentals”.

  • Docs: replication → Supports: one writer → Thesis

    PostgreSQL does not offer synchronous multimaster replication; in partitioning, only one server can modify each set. This note supports the thesis. It rests on 2 passages of “Comparison of Different Solutions”.

  • Release notes: 19 → Qualifies: version 19 → Thesis

    The version 19 release notes announce online table repacking and a command for reading one’s own writes on a standby. This note qualifies the thesis. It rests on 2 passages of “Release 19”.

  • Pavlo and Zhang, 2023 → Contradicts: storage → Thesis

    Pavlo judges the multiversion implementation the worst among the widely used relational systems he names. This note contradicts the thesis. It rests on one passage of “The Part of PostgreSQL We Hate the Most”.

The case against, and what was done with it

The note that contradicts the thesis rests on these words of The Part of PostgreSQL We Hate the Most:

its MVCC implementation is the worst among the other widely used relational DBMSs, including MySQL, Oracle, and Microsoft SQL Server.

Its sharper form is recorded as a rival reading, another way to read the same evidence:

PostgreSQL’s multiversion design is the worst among widely used relational databases, so its update costs are a reason against it.

Confidence recorded: low. Pavlo argues this and the documentation confirms parts of the mechanism. The research evidence read here is mixed and does not measure PostgreSQL, so the ranking is not established.

An objection to the report’s own evidence is recorded too:

Accounts of limits reached come from a few large companies that chose to write about them, and say little about the ordinary web application.

Confidence recorded: high. It follows from what the sources are: three engineering articles by operators of large systems, with no survey among the sources.

The research log says of one paper sought on this question: It cuts both ways: delta storage did about twice as well on rows of 100 attributes with one touched (p. 789), and append-only did better on the TPC-C-based test (p. 790). The report’s answer begins The objection therefore stands in a limited form. It goes on to say: It is not shown here that another database would do better.

6 The check

With the text of all 17 works present, the check ends with two problems open and nothing it could not check. This version also does not run 2 kinds of check that apply here. So the project is not checked clean.

The first problem: a reference and its page disagree

The page of the 9.6 release notes calls itself by a general title, and its first parts are menus. Stemma compares the record with those, and finds neither the record’s title nor its authors or year there. The page does give the release number and its date further down. The record was not changed to match the general title, which would make the reference worse.

Getting the text back

Ask Claude to fetch the text again, or give it your own copies of the originals. Stemma tries the places recorded for each work, or looks at your files, for one with the recorded fingerprint. It writes the missing text only if every part matches what the project recorded. Where a page now differs, it says that the copy fetched is not the recorded original, and writes the text only on the same condition. A web page can change at any time, so this may stop working for any of them. Until the text is back, the report cannot be rebuilt, and whether it is current cannot be told.

What no check shows

No check tells you that a source supports the sentence that cites it, that the argument holds, or that these are the right sources. Documentation says how software is meant to behave, not how it behaves under load. The research also has gaps:

  • No systematic search was run. An AI model chose the sources from what it already knew, which favors well-known documents.
  • Two articles are named as not used: OpenAI’s article of 2026 on scaling PostgreSQL, and Uber’s article of 2016 on leaving it. Nothing in the report rests on either.
  • Nothing in it measures PostgreSQL 18 or 19, compares current releases with other databases, or shows how often applications meet the limits discussed.
