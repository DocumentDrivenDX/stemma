# The Cost of One Writer

## PostgreSQL as a Web Application’s Default Database, and Where the Default Ends

### Abstract

This report asks when PostgreSQL is a sound default for a web application’s primary datastore. It argues that PostgreSQL 18 is one while the application’s writes fit comfortably on one primary server and someone attends to that server’s upkeep. The main costs follow from that single primary: a process for each connection, old row versions that must be reclaimed, finite transaction identifiers recycled by the same maintenance, and replication that copies writes without dividing them. Three operators’ accounts report trouble with this maintenance, in one case together with a limit on input and output, on large or heavily written databases. The accounts are few, self-selected and older than the current release, so they show where to look for the limit, not at what size an application will meet it.

## 1. Question and evidence

A default is sound if it serves the common case well and gives warning of the uncommon one. A sharp critic of PostgreSQL’s design grants the first point. In an article written with Bohan Zhang, Andy Pavlo describes the system in these words: “It’s dependable, feature-rich, extensible, and well-suited for most operational workloads.”[^1]

The version examined is PostgreSQL 18, read in its versioned documentation on 27 November 2026. PostgreSQL 19 had been released eight days earlier; its release notes are used only to show which limits are moving. The other evidence is the notes for PostgreSQL 9.6, the feature description of the connection pooler PgBouncer, two papers on concurrency control, the critique just quoted, and engineering accounts from Sentry, Notion and Figma. No measurements were made for this report.

## 2. What the default includes

Many of a web application’s defects are defects of concurrency. In PostgreSQL, “Read Committed is the default isolation level”,[^2] so an application that has chosen nothing does not have the strongest guarantee. That guarantee is available at the Serializable level, with a condition: “This level emulates serial transaction execution for all committed transactions; as if transactions had been executed one after another, serially, rather than concurrently. However, like the Repeatable Read level, applications using this level must be prepared to retry transactions due to serialization failures.”[^3] A whole transaction must be safe to run again. Dan Ports and Kevin Grittner, writing about the implementation that appeared in PostgreSQL 9.1, report from their experiments: “Our experiments show that this serializable mode provides performance similar to snapshot isolation and considerably outperforms strict two-phase locking on read-intensive workloads”.[^4] These are implementers’ results on an old release. They do not predict how often a given application’s transactions will collide.

A second common need is data whose shape is not settled. PostgreSQL has two JSON types, and its advice favors the binary one: “In general, most applications should prefer to store JSON data as jsonb”.[^5] A large JSON column is still one value in one row: “Although storing large documents is practicable, keep in mind that any update acquires a row-level lock on the whole row.”[^6] Requests that change unrelated parts of a large document therefore contend for it.

## 3. A process for each connection

The first limit is at the front door. “The PostgreSQL server can handle multiple concurrent connections from clients. To achieve this it starts (“forks”) a new process for each connection.”[^7] The number of connections is capped by a setting, and raising the cap is not free: “PostgreSQL sizes certain resources based directly on the value of max_connections. Increasing its value leads to higher allocation of those resources, including shared memory.”[^8] A web tier that grows by adding application instances, each holding connections of its own, presses on this cap.

A common answer is a pooler, which shares fewer server connections among many clients. In PgBouncer’s transaction mode a client holds a server connection only while a transaction lasts, and the project states the price: “This mode breaks a few session-based features of PostgreSQL. You can use it only when the application cooperates by not using features that break.”[^9] Its table of incompatible features includes session-level advisory locks, listening for notifications and several kinds of session setting and state. The pooler thus moves a rule into the application, which must not assume that two transactions share a session. The rule is easier to adopt at the start than to impose on code that already relies on session state. None of the material examined says how many connections a given server can sustain.

## 4. Old row versions

PostgreSQL lets readers and writers proceed together by keeping more than one version of a row. “In PostgreSQL, an UPDATE or DELETE of a row does not immediately remove the old version of the row.”[^10] An operation called vacuum reclaims the space later. Its ordinary form marks the space for reuse. “However, it will not return the space to the operating system, except in the special case where one or more pages at the end of a table become entirely free and an exclusive table lock can be easily obtained.”[^11] Vacuum normally runs by itself, and the documentation calls this enough for much ordinary use: “For many installations, it is sufficient to let vacuuming be performed by the autovacuum daemon”.[^12] It says many installations, not all.

Updates also cost work in indexes. “Specifically, updates require new versions of rows to be added to tables. This can also require new index entries for each updated row, and removal of old versions of rows and their index entries can be expensive.”[^13] An optimization called heap-only tuples avoids new index entries when two conditions hold. In the documentation’s words, the first: “The update does not modify any columns referenced by the table's indexes, not including summarizing indexes.” The second: “There is sufficient free space on the page containing the old row for the updated row.”[^14] Changing an indexed status or timestamp column therefore forgoes the saving. Pavlo and Zhang state the cost when an update does not qualify, writing of the work of adding entries to all of a table’s indexes: “Unless the DBMS stores the new version in the same page as the previous version (HOT update), the system does this for every update.”[^15] They also write of dead versions that “write-heavy workloads can cause them to accumulate faster than the vacuum can catch up, resulting in continuous database growth.”[^16]

## 5. A finite counter

Vacuum has a second duty with a hard edge. Transaction identifiers are 32-bit numbers compared in a circle, and old row versions must be marked as frozen before the counter comes round. “To avoid this, it is necessary to vacuum every table in every database at least once every two billion transactions.”[^17] PostgreSQL forces this work even where automatic vacuuming is otherwise disabled. If the work still falls too far behind, the server issues warnings and then stops assigning identifiers: “In this condition any transactions already in progress can continue, but only read-only transactions can be started. Operations that modify database records or truncate relations will fail.”[^18] The design prevents silent data loss, but a web application that cannot record anything is, in large part, down.

Sentry reported such an outage in 2015. David Cramer wrote: “One such problem caused a major outage of the hosted Sentry service earlier this week. That problem is Postgres’ transaction ID (XID).”[^19] The account says that the company had adjusted vacuum’s settings in order to avoid this situation. Service returned after the team emptied one very large table whose contents it could risk losing; as Cramer put it, “we made the decision that we were willing to risk all data in the table if it meant we could recover immediately.”[^20] He also wrote that “ultimately we’re going to be moving away from a SQL-based architecture.”[^21]

The account must be read with its date. According to the documentation of version 18, “contrary to what was sometimes recommended in earlier releases, it is not necessary or desirable to stop the postmaster or enter single user-mode in order to restore normal operation.”[^22] PostgreSQL 9.6, released in 2016, also reduced the work of the protective vacuum: “Formerly, anti-wraparound vacuum had to visit every page of a table, even pages where there was nothing to do. Now, pages containing only already-frozen tuples are identified in the table's visibility map, and can be skipped by vacuum even when doing transaction wraparound prevention.”[^23] The length of Sentry’s outage should not be taken as a guide to a current system. What carries forward is narrower. The counter is still finite, and staying clear of its end still depends on maintenance keeping pace.

## 6. One writer

PostgreSQL can keep standby servers current by sending them its log of changes. The default favors speed over certainty: “PostgreSQL streaming replication is asynchronous by default. If the primary server crashes then some transactions that were committed may not have been replicated to the standby server, causing data loss. The amount of data loss is proportional to the replication delay at the time of failover.”[^24] The documentation estimates the delay before a change is visible on a standby in these terms: “Streaming replication is asynchronous by default (see Section 26.2.8), in which case there is a small delay between committing a transaction in the primary and the changes becoming visible in the standby. This delay is however much smaller than with file-based log shipping, typically under one second assuming the standby is powerful enough to keep up with the load.”[^25] The condition at the end matters. An application that writes to the primary and at once reads from a replica may not find what it wrote. A commit can instead be made to wait for standbys, even until they have applied it, and this can be chosen for individual transactions. The price is latency: “As a result, incautious use of synchronous replication will reduce performance for database applications because of increased response times and higher contention.”[^26]

Standbys of one primary add places to read and a server to fail over to, but no second place to send the same writes. Other arrangements exist, among them logical replication in several directions and external tools, with their own demands for routing or conflict handling. One is absent. Of synchronous multimaster replication, in which every server accepts writes and passes them to the others before commit, the documentation says: “PostgreSQL does not offer this type of replication”.[^27] Another way to spread writes is to split the data. “Data partitioning splits tables into data sets. Each set can be modified by only one server.”[^28] A query that spans the sets must then be assembled by the application or served from copies.

Two accounts describe teams that took that road. Garrett Fidalgo wrote of Notion in 2021: “For us, the inflection point arrived when the Postgres VACUUM process began to stall consistently, preventing the database from reclaiming disk space from dead tuples.”[^29] The greater worry, he adds, was exhausting transaction identifiers. His general lesson is that “Query performance and upkeep processes often begin to degrade well before a table reaches the maximum hardware-bound size”.[^30] Notion divided its data by workspace across many databases and routed queries in the application.

Figma’s account, by Sammy Steele in 2024, describes a longer course. The company first worked to reduce processor use and added caching, read replicas and a division of tables among a dozen databases. Some tables then outgrew that remedy. “At this size, we began to see reliability impact during Postgres vacuums, which are essential background operations that keep Postgres from running out of transaction IDs and breaking down.”[^31] Writes pressed from another side: “Our highest write tables were growing so quickly that we would soon exceed the maximum IO operations per second (IOPS) supported by Amazon’s Relational Database Service (RDS).”[^32] The account states this second limit as one of the managed service Figma used. Because the earlier division could not split a table, the company set out to spread single tables across servers.

Figma did not leave PostgreSQL. It judged a migration to another distributed database too risky for its deadline, and of non-relational stores it wrote: “However, we have a very complex relational data model built on top of our current Postgres architecture and NoSQL APIs don’t offer this kind of versatility. We wanted to keep our engineers focused on shipping great features and building new products instead of rewriting almost our entire backend application; NoSQL wasn’t a viable solution.”[^33] These are reasons to stay that belong to an application already built; they do not show that PostgreSQL was the best first choice. The account is also plain about what splitting tables costs: “Schema changes must be coordinated across all shards to ensure the databases stay in sync. Foreign keys and globally unique indexes can no longer be enforced by Postgres.”[^34] PostgreSQL can no longer enforce a transaction that crosses shards either. Other sharding designs make other trades, but here dividing a relational database changed what the application could assume. The first sharded table took the team about nine months.

## 7. The case against the design

The strongest objection to the default is that these troubles follow from a design that other systems avoid. Pavlo and Zhang say of PostgreSQL’s method of keeping row versions that “its MVCC implementation is the worst among the other widely used relational DBMSs, including MySQL, Oracle, and Microsoft SQL Server.”[^35] Their grounds are that an update writes a whole new row, that dead and live versions share storage, that updates outside the favorable case touch every index, and that cleanup is hard to tune. The documentation confirms important parts of the mechanism. It does not rank PostgreSQL against other systems.

Research comparing such designs gives a mixed answer. Yingjun Wu and colleagues, Andrew Pavlo among them, studied ways of storing row versions and classed PostgreSQL with systems that append each new version to the table. Of the schemes compared they write: “These schemes have different characteristics that affect their behavior for OLTP workloads. As such, none of them achieve optimal performance for either workload type.”[^36] One result favors the critic. With rows of a hundred attributes, in reads and updates that each touched one, they report that “the delta scheme achieves ∼2× better performance than append-only and time-travel schemes because it uses less memory.”[^37] Another runs the other way. In a test based on the TPC-C benchmark, “The results in Fig. 17a show that append-only storage achieves comparatively better performance than the other two schemes.”[^38] Neither is a measurement of PostgreSQL. The authors built each scheme into one research system: “We then implemented them in the Peloton DBMS and evaluated them using OLTP workloads to highlight their trade-offs.”[^39]

The objection therefore stands in a limited form. Where the workload is dominated by updates to heavily indexed rows, PostgreSQL’s storage design is a reason to test the expected update pattern before committing, and to watch how many updates take the heap-only path and whether vacuum keeps up. It is not shown here that another database would do better. Uber’s 2016 account of leaving PostgreSQL, often raised on this point, was not retrieved and is not relied on.

## 8. Limits that move

A judgment about limits ages. The 2016 change is one example. The release notes for PostgreSQL 19 now announce a new command for reclaiming space: “New REPACK command that reclaims disk space and reorganizes table contents, which can improve query performance. REPACK (CONCURRENTLY) allows repacking without blocking reads and writes to the table.”[^40] They also announce parallel autovacuum of a table’s indexes and a new order of priority for automatic vacuuming. For replicas, the list includes this: “Support for “read-your-writes” consistency on standbys via the new WAIT command.”[^41] As read for this report, they announce no end to the 32-bit transaction counter. The release was eight days old, and no account of it in production was examined.

## 9. Conclusion

The evidence supports PostgreSQL as a default, on conditions best written down when the default is taken. Plan for pooling early, and keep session state from spanning transactions. Monitor vacuum as part of the system, including the age of the oldest transaction identifiers and the growth of dead versions. Decide which reads may be stale and which commits must survive the loss of the primary. Watch the largest and most heavily written tables, where the operators’ accounts place the trouble. Treat dividing data among writers as a design change to begin while the server still has room; looking back, Notion’s account says that “we waited until our existing database was heavily strained”.[^42]

The default needs a different plan from the start where the requirement is already known to exceed it, as when several sites must all accept the same writes synchronously, or when the expected write volume is more than one server is known to carry. For workloads made mostly of updates to indexed rows, the verdict is open and calls for a test.

Two kinds of evidence could change this assessment: a survey of how often applications of ordinary size meet these limits, since companies that write about scaling are no sample, and a controlled comparison of current databases on update-heavy work.

## 10. Scope

This is a reading of a small set of documents chosen for their bearing on the argument, not a survey. Documentation states how PostgreSQL is designed to behave and is not independent evidence of its behavior under load. The operators’ accounts are first-hand and unaudited, date from 2015 to 2024 and concern large systems. Figma and Notion describe running PostgreSQL on Amazon’s managed service, so some of their limits may be the provider’s. Managed services, distributed extensions of PostgreSQL, upgrades, failover tools, backup, cost and comparisons of features with other databases are not examined. Web documents without page numbers are cited by paragraph, counted through a stored copy from the top of each page, navigation included; the numbers do not appear on the pages. The two papers are cited by page.
